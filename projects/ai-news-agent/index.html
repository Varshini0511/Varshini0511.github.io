AI News Agent

A scheduled agent that filters the AI news firehose

A serverless agent that watches AI blogs, release feeds, newsletters and forums, has an LLM score every new item against my own definition of relevant, and pushes only the worthwhile ones to Telegram and a rolling digest. It also watches pages that have no feed for new credit and student offers.

Source

No hosted UI: it runs as a scheduled GitHub Actions job and delivers to a private Telegram chat. Its output is the digest.md file the agent rewrites in the repository.

Role

01 / The problem

AI news moves faster than anyone can read, and the signal — a model release, an API change, a time-limited free-credit offer — is buried in hype and reposts. I wanted a filter built on my own definition of relevant, running without a machine of mine switched on, that interrupts me only for the rare item that matters.

02 / What it does

  • Scores new items from 28 feeds — blogs, GitHub releases, newsletters, forums — against plain-English interests kept in a config file
  • Batches 25 items per model call and keeps those scoring 6 or more, each with a one-sentence reason it matters
  • Provider fallback across Gemini, Grok, Groq and Claude: each configured provider is tried in order and the next takes over on error or quota
  • Watches 8 pages that have no feed, diffs their text between runs and asks the model whether the change is a new credit, student or grant offer
  • Breaking items (9 and above) arrive on Telegram one by one; everything else arrives as a single bundled digest
  • Runs every 30 minutes on GitHub Actions with no server; seen links and page snapshots are committed back to the repository
  • Also keeps a rolling digest.md and can email each digest; every delivery channel is optional

03 / How it works

Scoring a firehose with one call per 25 items

New items are batched, each reduced to its source, title and the first 300 characters, and sent with a system prompt that reserves 9 and 10 for the rare breaking item and rates routine posts and research 6 to 8. The model replies with a JSON list of id, score and summary. The parser slices from the first bracket to the last, and a malformed reply is logged and skipped rather than failing the run. The interests live in a YAML file in plain English, so changing what counts as relevant never touches code.

Provider fallback instead of a single point of failure

Free-tier model quotas run out at inconvenient moments, and a scheduled job has nobody watching it. The same call goes to Gemini, Grok and Groq through their OpenAI-compatible endpoints, then to Claude through its own SDK. Providers without a key are skipped, the order is an environment setting, and when every provider fails the error lists each one's reason. It is a cheaper answer to quota limits than retry logic.

Watching pages that have no feed

For the pages with no RSS, the agent keeps a text snapshot, diffs the new text against it and sends only the added lines to the model, which answers either “no” or a sentence on what the offer is, who is eligible and any deadline. The first run only records a baseline. Anything that passes is scored 10 and goes out as breaking.

No server, no database

The schedule, the runtime and the state all live in GitHub. A workflow runs every 30 minutes, with secrets held as repository secrets, and commits the list of seen links, the page snapshots and the digest back to the repository, so the next run knows what it has already handled. The seen list is capped at the latest 5,000 links. Telegram messages fall back to plain text when Markdown parsing is rejected and are truncated to the platform's length limit.

Known gaps, stated

There are no automated tests and no labelled set to measure whether the scores match my own judgement. A watched page whose text keeps changing can raise the same offer alert on consecutive runs; hashing only the relevant content is the next fix. An item is marked seen even if its Telegram or email delivery failed, so it survives only in digest.md. And Telegram is one-way for now: it pushes alerts but does not answer questions, which is the extension I would build next.

04 / Run it locally

  • ›Read digest.md in the repository — it is the agent's live output
  • ›pip install -r requirements.txt, then set one model key and, optionally, a Telegram bot token and chat id
  • ›python agent.py --test sends a test message to every configured channel
  • ›python agent.py --loop 30 runs it locally; edit sources.yaml to change the interests and feeds
  • ›Fork the repository and add the keys as repository secrets to run it on the schedule

05 / What I took away

  1. 1.Free-tier model quotas will fail at the wrong moment; a provider fallback chain is cheaper than retry logic.
  2. 2.Treat model output as untrusted text: parse defensively, and log and skip rather than abort the run.
  3. 3.When state is small and its history is useful, a scheduled job can keep it in the repository itself.
  4. 4.A filter needs a written definition of relevance; moving it into a config file made it tunable without code changes.
  5. 5.Decide what happens to an item when delivery fails. Marking it seen anyway is the wrong default.
