RideSmartAgent

Ride-hailing price comparison and race booking for India

An agent that compares live prices across Uber, Ola, Rapido and Namma Yatri, decides between a cab and an auto, and then books by racing the cheapest providers against each other — first driver confirmation wins. It learns from your ride history to flag unusual prices and predict surge.

Source

No hosted demo: it drives real, logged-in Uber and Ola browser sessions, so it runs locally on your own accounts.

Role

01 / The problem

Getting the cheapest ride in India means opening four apps, comparing by eye, and then hoping the driver you chose accepts. Prices move by the minute, and the cheapest quote is worthless if nobody confirms it. I wanted to automate the whole loop — compare, decide, book, and fall back — and make it smarter the more it is used.

02 / What it does

  • Live price comparison across Uber and Ola via Playwright, with distance-based fare estimates for Rapido and Namma Yatri
  • Cab-versus-auto decision logic with a configurable price threshold and a plain-English reason for every recommendation
  • Race booking: providers priced within ₹50 of the cheapest are booked at once, and the first confirmed driver wins
  • Sequential fallback booking as an alternative — try the top pick, move to the next on failure or timeout
  • Anomaly detection using z-scores against your own route history, with warning and alert severities
  • Price prediction, surge probability and best-time-to-book from historical patterns
  • Groq-powered chat assistant grounded in your frequent routes, provider preferences and current quotes

03 / How it works

Browser automation as the integration layer

Each provider sits behind one abstract RideProvider class — fetch_quotes, initiate_booking, check_booking_status, get_deep_link — so adding a fifth is a matter of implementing four methods. Underneath, each provider drives its own Playwright browser context with a persistent login session saved to disk, so you sign in once and the agent reuses it. Contexts present a mobile viewport and user agent so the mobile web flows render. The honest cost of this approach is fragility: selectors change, and a scraper is only as stable as the page it reads.

One slow provider can't sink the comparison

Quotes are fetched from every provider concurrently with asyncio.gather, and each fetch is wrapped in a timeout and a catch-all. A provider that times out or throws returns an empty list and a logged reason rather than an exception, and the failure is recorded against that provider so the UI can say what happened. Treating the least reliable component as expected-to-fail is what keeps the whole flow usable.

Decision logic, not just sorting

The comparator makes a real product decision. If the cheapest cab is within the budget threshold (₹380 by default, configurable), cabs are ranked first with autos as the fallback. If every cab exceeds it, the ranking flips to autos first. Whichever way it goes, the output is a full ranked list plus a human-readable reason, so a failed first choice always has a next one ready and the user can see why it was picked.

Race booking

The cheapest quote is worthless if no driver accepts it, so booking races. The orchestrator takes the cheapest option per provider within ₹50 of the overall best, initiates a booking on each, then polls them together. The first to report a confirmed driver wins and the others are closed down; a provider that reports no drivers drops out of the race on its own, and a global timeout (120s by default) ends it if nobody confirms.

Learning from history with simple statistics

Every comparison is written to a SQLite history. Price prediction averages past prices for the same route, provider and hour, widening to adjacent hours, the same weekday, then the whole route when data is thin — and the confidence it reports falls accordingly. Anomaly detection flags a quote more than two standard deviations from that route's history, and needs at least three samples before it will say anything. These are statistical methods rather than trained models, which is deliberate: with one person's ride history there isn't enough data to train anything, but there is enough for simple, explainable numbers.

An assistant grounded in your data

The Groq chat assistant doesn't answer from a generic prompt. Its system prompt is assembled per request from your most frequent routes, how often you've chosen each provider, the historical price stats for the route in question, and the quotes currently on screen — so “should I wait?” gets an answer based on your own patterns.

04 / Run it locally

  • ›pip install -r requirements.txt && python -m playwright install chromium
  • ›cp .env.example .env — add GROQ_API_KEY and GOOGLE_API_KEY (both optional)
  • ›python -m ride_smart.login_setup uber — one-time login, repeat for ola
  • ›streamlit run ride_smart/streamlit_app.py --server.port 8502
  • ›Compare a route twice at different times — anomaly detection and prediction start to fill in

05 / What I took away

  1. 1.The least reliable component — here, scraping — should be isolated, time-boxed and expected to fail.
  2. 2.With a single user's data, simple statistics with an explicit confidence beat a model with nothing to learn from.
  3. 3.Fallback order is a product decision; putting it in one function with a readable reason keeps it debuggable.
  4. 4.Some systems cannot be hosted as a demo; say so instead of faking one.
