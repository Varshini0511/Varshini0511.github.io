AgentCustody

A tamper-evident chain of custody for AI agent tool calls

A proxy that sits between an AI agent and its MCP tools, writes every tool call down before it runs, and makes that record impossible to change quietly: edit, delete, insert, reorder or cut off one record and custody verify names the line. Per-tool rules allow a call, block it, or hold it until a person approves.

Source

No hosted demo: it is a command-line tool you install with the .NET SDK. The repository has a Claude Code demo and a tamper lab that run on any machine.

01 / The problem

AI agents now write files, send email and act on real accounts. When something goes wrong, the first question is what exactly the agent did and who allowed it, and an ordinary log cannot answer that with confidence, because anyone with access can edit it. On the forensics platform I work on, evidence is worthless unless you can prove nobody changed it since it was collected. I wanted to apply that same chain of custody to what agents do, in .NET, and make it cheap enough to sit in front of every tool call.

02 / What it does

  • A stdio MCP proxy: put custody proxy in front of any server's command and it works with Claude Code, Claude Desktop or any MCP client
  • Every tool call is recorded before it runs and every result before the agent sees it; if a record cannot be written, the call does not run
  • Three layers of protection: a SHA-256 hash chain, an ECDSA P-256 signature on every record, and a witness file kept in a separate folder
  • custody verify reports the kind of change and the exact line: edited, deleted, inserted, reordered, truncated or forged
  • Rules per tool: allow, block, or hold the call until a person runs custody approve or deny from any terminal; no answer in time means no
  • Secrets are masked before they reach the log, by key name and by known formats such as sk-, ghp_ and AKIA
  • Fingerprints every tool definition and warns when a server quietly changes one between sessions, a known MCP attack
  • Exports a signed evidence bundle (logs, witness, public key and a signed manifest) that anyone can verify
  • A one-file Python writer with the same format, used by AyvaBot to record every tool its agents run
  • 49 tests on Windows and Linux CI, including end-to-end runs through the real proxy and Python ↔ .NET interop

03 / How it works

Chain of custody, applied to agents

In digital forensics an item of evidence carries a record of everyone who handled it, and any gap makes it inadmissible. AgentCustody treats an agent's actions the same way. Each session starts with a record of who, where, which signing key and the hash of the policy in force; then every tool list, call, approval and result is appended; and the session ends with a seal. A reviewer can later prove which rules applied and that nothing was changed since.

Three layers, each catching what the last can't

Each record stores the SHA-256 of the one before it, so editing, deleting, inserting or reordering a record breaks the chain. A careful attacker could edit a record and recompute every hash, so each record is also signed with an ECDSA P-256 key the attacker does not have. Neither catches records simply cut off the end, so after every record its sequence number and hash are also written to a witness file in a separate folder, which also shows when a whole session's log has been deleted.

Hash the bytes, not the object

The hash covers the exact bytes written to the line, minus the final hash and signature fields, and verification never re-serialises the JSON. Two JSON libraries can disagree on spacing, escaping or number formats, and that would make an honest log look tampered. Hashing bytes is why a Python writer and the .NET verifier agree on every line, and the test suite checks it by running the real Python writer and verifying its output in .NET.

Fail closed, record first

The proxy forwards raw JSON-RPC rather than using an MCP SDK, so every method and protocol version passes through untouched and only tools/call and tools/list are inspected. Batched requests are split, so no call inside a batch can skip the rules. A call is recorded before it reaches the server and a result before it reaches the agent; if recording fails, the call is dropped. A blocked call returns a clear error telling the agent the attempt was recorded and not to retry.

A person in the loop, from any terminal

A rule can hold a call until someone decides. The request appears in a small file-based queue: custody approvals lists what is waiting and custody approve or deny answers it, while the agent waits. If nobody answers within the time limit the call is refused. The log records the decision, who made it and how long it took, so an approval is evidence too, not just a click.

Measured

A built-in tamper lab runs six attacks on copies of a real log, and all six are caught. Without the public key, the witness alone still catches all six; without the witness, cutting off the end is reported as a warning, never as intact. Over 1,000 calls through the proxy the added latency was 0.74 ms at p50 and 0.99 ms at p95, including hashing, signing, the witness write and the extra process hop, and the resulting 2,102-record log verified intact.

Known gaps, stated

Someone holding the private key can forge a whole new log; the key sits in the user profile, and moving it to Azure Key Vault or a TPM is the next step. The witness is on the same machine by default, which raises the bar but is not independent storage. Rules match tool names, not argument values. And a proxy only sees what passes through it: in my own testing Claude Code used its built-in file tool and skipped the proxy entirely, so those tools have to be turned off, or recorded through Claude Code's hooks, which is planned next.

04 / Run it locally

  • ›custody tamper <log> all — six attacks on copies of a real log, each caught and explained
  • ›Copy a log, change one word in Notepad, then run custody verify on the copy — it names the line
  • ›From demo/workspace, start Claude Code with ../claude-mcp.json, ask it to write and then rename a file, approve the write with custody approve and watch the rename get blocked
  • ›custody show — the session as a table: what ran, what was blocked and who approved
  • ›custody bench --calls 1000 — measure the added latency on your own machine
  • ›dotnet test — the 49-test suite

05 / What I took away

  1. 1.A log that matters needs the same chain of custody as forensic evidence: hash it, sign it and keep a witness somewhere else.
  2. 2.Hash the exact bytes you wrote; re-serialising JSON to check it is how two languages quietly disagree.
  3. 3.Fail closed: an action that could not be recorded should not happen.
  4. 4.The safe default for an approval nobody answers is no.
  5. 5.A proxy only protects what goes through it; state that boundary and test it, because an agent will happily use another door.
