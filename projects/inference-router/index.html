inferouter

A cost-aware LLM inference router with a confidence cascade

An OpenAI-compatible gateway that serves most traffic from a small self-hosted model (vLLM) and escalates only the hard requests to a larger one. A difficulty router decides up front, a confidence cascade corrects its mistakes from the model's own token log-probabilities, and a cost model states when any of it pays for itself.

Source

No hosted demo: it is a gateway you run yourself. It works end to end with no GPU and no API keys — make serve starts it on deterministic mock backends — and a config file points it at real vLLM and provider endpoints.

Solo — router, cascade, gateway, cost model, evaluation

The problem

Sending every request to a frontier model is simple and expensive; most traffic is easy and a small model answers it for a fraction of the cost. But routing is a bet — the router will sometimes send a hard prompt to the small model. I wanted to build the whole production shape (gateway, router, safety nets, cache, rate limits, metrics) and, more importantly, be precise about the economics: a self-hosted GPU costs money around the clock, so savings only exist above a break-even volume.

Architecture

What it does

  • OpenAI-compatible: existing clients switch by changing one base URL; every response carries an x_router block with tier, p_hard, escalation, cache hit and cost
  • Three interchangeable routers behind one interface — a transparent heuristic, TF-IDF + logistic regression, and an offline LSA embedding classifier — compared on accuracy, F1 and ROC-AUC
  • N ordered tiers: add a mid tier with one config entry and the cascade escalates one hop at a time
  • A confidence cascade driven by the serving model's own token log-probabilities, plus a separate availability fallback when a tier is down
  • Streaming over SSE, a paraphrase-aware semantic cache, token-bucket rate limiting and per-tenant thresholds
  • Prometheus metrics by tier: requests, cost, tokens, latency, escalations, cache hits and rate-limits
  • A cost report that leads with break-even volume and a volume × price sensitivity table, not one flattering number
  • 46 tests and CI; runs with no GPU and no API keys through deterministic, capability-driven mock backends

How it works

A router is a bet, so build the net first

The router predicts the probability a prompt is hard from the last user turn only — a long, constant system prompt would otherwise dominate the score — and thresholds map that probability to a tier. Two tiers is a single threshold; three tiers with [0.4, 0.8] sends under 0.4 to small, under 0.8 to mid and the rest to large. Any classifier will sometimes be wrong, and a hard prompt sent to a small model is a quality failure, so the system is designed around two independent safety nets rather than around trusting the router.

Using the model's own uncertainty

The cascade reads the mean token log-probability of the answer the small model just produced. If it falls below a configured floor, the request is re-asked one tier up, and that repeats while the serving model stays unsure. It catches the router's misses using signal the model already emits, with no second classifier to train; a failed escalation simply keeps the earlier answer. The limit is stated plainly: streaming skips the cascade, because judging confidence needs the full completion, and buffering the first tokens to recover it is the documented next step.

Availability is a separate problem

Quality and uptime fail differently, so they get separate mechanisms. If the chosen tier errors or times out, the fallback degrades to the nearest other tier, preferring the more capable one on a tie. On the streaming path the first chunk is pulled before anything is committed to the client, so an outage is detected before a single token is sent and the request can move to another tier cleanly.

Three routers, one interface

The heuristic scores reasoning verbs, code fences, maths and length through a logistic squash and needs no training; the learned router is TF-IDF with logistic regression; the third is a dense LSA embedding with the same classifier on top. All expose the same score(prompt) function, so they can be swapped by config and compared with one script. If a trained artefact is missing the system falls back to the heuristic and logs it. On the synthetic set the learned routers hit a perfect score, which mostly reflects template vocabulary; the heuristic's imperfect 87% accuracy is the more realistic signal.

The economics

A self-hosted tier has no per-token price but a fixed, always-on GPU cost, so savings only appear above a break-even volume — fixed daily cost divided by the saving per request. That is why the report leads with break-even and a sensitivity table rather than one headline. In the repo's own simulation, at 10,000 requests a day the saving is thin (about 3%, with break-even near 9,400 a day), it grows to roughly 46% at a million a day, and at 1,000 a day the GPU costs far more than it saves. The negative cells are the point: they show where this architecture is the wrong choice.

A production surface, not a script

Streaming uses OpenAI-style SSE chunks with the routing metadata on the final one. The semantic cache matches paraphrases with a hashing embedding and cosine similarity under LRU eviction, behind an interface that maps onto Redis and a real embedder. A per-tenant token bucket returns 429s, API keys carry their own thresholds so a premium tenant routes to bigger models sooner, a header can pin a tier, and a dry-run endpoint reports which tier would serve a prompt without making a model call.

What the numbers do and don't prove

The workload is synthetic and the backends are mocks driven by ground-truth labels, so the simulation validates the routing, cascade and cost logic, not real-world accuracy, and "quality retained" is a proxy rather than a measured answer-quality score. The repository says so itself and documents the real evaluation: label a sample of traffic or use RouterBench or LMSYS-Chat, retrain the router, point the config at live vLLM and provider endpoints, and measure with the load-test script.

Run it locally

  • ›make install && make test — the 46-test suite
  • ›make demo — trains the router and writes the 10,000-requests/day cost report
  • ›make eval — compares the three routers on accuracy, F1 and ROC-AUC
  • ›make serve, then call /v1/chat/completions with an easy and a hard prompt and compare x_router.tier
  • ›POST /v1/route/explain — see which tier would serve a prompt without spending anything
  • ›python scripts/simulate.py --config configs/three_tier.yaml — a three-tier run with cache, rate limit and per-tenant thresholds

What I took away

  • Routing is a bet; the cascade and the fallback are what make it safe to place.
  • A model's token log-probabilities are a free confidence signal — often enough to catch a router's misses without training another classifier.
  • Self-hosting changes the cost shape to zero per-token but a fixed bill, so report break-even, not a headline saving.
  • A synthetic benchmark that scores 100% says more about the data than the model; state that, and state how to test it on real traffic.
