AdviShopping

Production-shaped retrieval for e-commerce

A full-stack shopping platform built around a real retrieval stack rather than a SQL LIKE query. Three distinct search modalities — text, image and voice — over the same Postgres + pgvector catalogue, plus a document-extraction endpoint that turns invoices, receipts and datasheets into validated JSON.

01 / The problem

Almost every shop demo searches with WHERE name ILIKE '%query%'. That fails the moment a shopper describes what they want instead of naming it — “device to call someone” matches nothing, because it shares no words with “iPhone”. I wanted to build the retrieval stack a real product would need, and then show it worked with measurements rather than impressions.

02 / Capabilities

A six-stage pipeline. Postgres full-text (tsvector + GIN) and pgvector semantic search run as parallel candidate generators, get unioned, then sorted by Reciprocal Rank Fusion with tunable keyword/semantic weights. A ms-marco-MiniLM cross-encoder reranks the survivors behind a confidence guard, and an LLM writes the recommendation with per-product reasons.

  • 6 stages: FTS → pgvector → merge → RRF → cross-encoder rerank → LLM
  • Metadata filters pushed inside both retrieval subqueries, not applied after
  • Embeddings and reranking run on-device via Transformers.js — no API key
  • “device to call someone” returns phones despite zero shared words

03 / How it works

Why Reciprocal Rank Fusion

Keyword and vector search return scores on incompatible scales — a BM25 score and a cosine distance cannot be added or averaged meaningfully. RRF sidesteps this entirely by scoring on rank position rather than raw score, so the two result sets can be fused without normalisation. Weights stay tunable, so the keyword/semantic balance can be shifted per query type.

Filtering done correctly

The tempting shortcut is to retrieve first and filter the results afterwards. That quietly breaks recall: if you ask for the top 20 and then filter to in-stock items under ₹5,000, you can end up with two results when the catalogue holds fifty. Filters are therefore pushed into both the keyword and semantic subqueries, so each returns a full candidate set that already satisfies the constraints.

Proving it works

An evaluation harness (npm run evaluate) scores four strategies — keyword only, semantic only, hybrid, and hybrid plus reranking — against 20 labelled queries using precision@k, recall@k and NDCG@k. The measured result is candid: keyword-only reaches 58% NDCG@5 because it returns nothing for meaning-based queries, while semantic, hybrid and reranked all land at 99%. On a catalogue of about 32 products semantic search alone saturates the benchmark, so the gain from fusion and reranking is small here and would only show on a larger, noisier corpus. The harness is what makes that statement provable, and it justified switching the reranker off on the small production host, where +0.3% NDCG was not worth about 80 MB.

Running models on-device

Embeddings and reranking run in the Node process through Transformers.js rather than a hosted API — no key required, no per-query cost, no network hop. The trade-off is memory: roughly 110 MB of models load into the process, which is why this needs a persistent host rather than short-lived serverless functions, and why the reranker and visual search sit behind feature flags.

Document extraction you can trust

A model's JSON is only a proposal. It is validated against a typed schema that also normalises US and European number formats, dates and currency symbols; a failure sends the exact errors back once, never in a loop; and arithmetic cross-checks turn the document's own redundancy into a review flag. On a labelled set of 13 documents, all 13 were extracted as labelled and the one invoice with a wrong printed total was flagged while the model left the paper's figure intact. Running it also exposed two of my own mistakes: a provider outage that looked like an accuracy failure, and a prompt that stripped the comma from “4,800 mAh”. The set is small and synthetic, and I tuned the prompt after the first run on it, so it shows the method works rather than accuracy on arbitrary paperwork.

Tested, and watched in production

Seventy-two unit tests run in CI on every push: the agent's database writes against a fake client, including that the user always comes from the session and never from model arguments; the extraction engine with the model mocked; content-based file-type detection; and the rate limiter. A daily workflow visits the live site and fails if real product links are missing, which doubles as a smoke test and keeps the free-tier database from being paused for inactivity, and a health endpoint returns 503 when the database is unreachable so an uptime monitor can alert. Browser-level end-to-end tests are not written yet.

Hardened for the public internet

A deployed demo is a public endpoint, so it is treated like one. Chat, image and document routes are rate-limited per client; uploads are accepted by their actual leading bytes and size-checked before the body is buffered; a Content-Security-Policy and other security headers are set; dependencies are audited and pinned past known advisories; and a password-reset flow answers identically whether or not an address has an account. One fix is worth calling out: the app no longer ships raw embedding vectors to the browser — they stayed server-side once I realised the client never needed them. Small leak, but exactly the kind a review is supposed to catch.

05 / What I took away

  1. 1.Query and corpus embeddings must come from the same model, or vector search is meaningless.
  2. 2.Reranking is expensive, so a confidence guard decides when it's worth running at all.
  3. 3.Evaluation harnesses change how you work — you stop guessing whether a change helped.
  4. 4.A public demo is a public endpoint — rate limits, upload validation and not over-sharing data with the client are part of the build.
  5. 5.A bad result is not always a bad model: an outage and my own prompt each looked like an accuracy problem until I read the failures.
