RideSmart Android

Native app that reads live fares off the ride apps' own screens

A native Kotlin and Jetpack Compose app that compares live fares across Uber, Ola, Rapido and Namma Yatri by reading each app's own screen through an AccessibilityService, groups them by ride category and hands the booking to the app you choose.

Source

No hosted demo: it needs the ride apps installed and the Accessibility permission granted, so it is built from source on a device.

Role
Solo — native Android, accessibility screen reading, OEM-resilient design
Year
2026
Status
Open source · runs locally
Focus
Mobile · Android · Automation

01 / The problem

On a phone the four ride apps are one tap apart, but their fares can't be compared without opening each, remembering the number and switching back — and there is no fare API to call. The phone already shows the real price on screen, so I built an app that reads it from there. A fully automatic version failed on the aggressive battery managers that freeze background apps, so the shipped design is tap-to-read: you tap an app, RideSmart opens it on your route, reads the list and snaps back.

02 / What it does

  • Reads live fares from Uber, Ola, Rapido and Namma Yatri off each app's own screen via an AccessibilityService
  • Tap-to-read: user-initiated taps are never frozen by OEM battery managers, which killed the fully automatic first design
  • Scrolls each ride list so options below the fold are captured, and sorts vehicles into four categories
  • Uber and Ola open on the route by deep link; Rapido and Namma Yatri have none, so the destination is typed in
  • A foreground service and disk-persisted route and prices survive process kills; screen reading runs off the UI thread
  • Best Price and Fastest Pickup within each category, with the saving computed like for like
  • A built-in debug view shows exactly what was read, including the raw screen text for any app that returned nothing

03 / How it works

The phone already shows the price

There is no fare API to call, but the ride apps render their prices on screen, and an AccessibilityService can read another app's window. The service walks the visible nodes for rupee amounts, ETA minutes and vehicle names, and filters out promotional lines such as “save ₹20” so a discount is never mistaken for a fare. The result is the real number the rider would see, not a model of it.

Two ways to read an app's list

Uber and Rapido render each ride as one combined text node — name, fare and ETA together — so the extractor scans each node for every name-to-price pair. Ola puts the name and the price in separate nodes, so they are paired by sharing a screen row. Promotional lines such as “save ₹20” are filtered, and the list is scrolled so options below the fold are not missed.

The design that failed, and what replaced it

The first version was fully hands-off: RideSmart opened all four apps itself in the background. On Vivo, iQOO, Xiaomi and Oppo handsets the OS froze or killed the app the moment it was backgrounded, so it got stuck. I changed the design rather than fighting the OS: each read is now started by a tap, which is never blocked, and the route and captured prices are written to disk so even a hard process kill restores the results screen. The old automatic loop is still in the code, unused.

Why it does not book for you

I built a booker that requested rides across several apps and cancelled the losers, then took it out of use. Automatic booking and cancelling across apps was unreliable, and risky for the rider: cancellation fees and possible account bans. Book now simply opens the chosen app on the route for you to confirm yourself. The unused code remains, documented as experimental.

Comparing like with like

Comparing an auto with an SUV isn't a saving, so vehicle names are classified into four categories — auto, bike, mini or cab, sedan or SUV — in an order that matters (“Go Sedan” is a sedan, “Go Priority” is a mini). Suggestions and savings are then computed within each category.

The limits, stated

Each app needs a tap and roughly 10 to 20 seconds, and occasionally a retry; that is inherent to reading a screen and cannot be tuned away. Google Pay blocks payments while the accessibility service is on, because it looks like a scam app to Google's anti-fraud checks, so the permission must be switched off to pay; no money is at risk, it is a precautionary block. Rapido and Namma Yatri are accurate when the pickup is the current GPS location. The reliable route to an instant, official comparison is a data partnership, or ONDC for Namma Yatri, which is a business project rather than an app.

04 / Run it locally

  • ›Open the project in Android Studio and run it on a device (minSdk 26, Android 8.0+)
  • ›Enable RideSmart under Accessibility settings and allow Display over other apps
  • ›Install the ride apps you want compared and sign in to them
  • ›Enter a pickup and drop, choose ride categories and tap Compare
  • ›Tap each app to read its live price; RideSmart snaps back when it has the list
  • ›Open the Debug view if an app returns nothing, then tap Book to finish in the chosen app

05 / What I took away

  1. 1.When there is no API, the screen is the interface — and then timing and failure handling are the whole job.
  2. 2.OEM battery managers are a runtime you design for, not an edge case.
  3. 3.Compare like with like: a saving across different vehicle classes isn't a saving.
  4. 4.Know what not to automate: booking and cancelling across apps carries real cost to the user.
  5. 5.When the platform fights the design, change the design: a user tap beat every attempt to keep a background loop alive.
  6. 6.Reading another app's screen is powerful and sensitive; it belongs on the user's own device, with explicit permission, for their own rides.
