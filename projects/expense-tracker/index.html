ExpenseTracker

A tool-calling agent that takes real actions

An expense system where the AI does more than answer: it checks company policy via RAG, decides whether an expense is compliant, and then writes it to the database itself.

Live demo Source

Solo — agent service, RAG policy check, API, dashboard

The problem

Most agent demos stop at generating text. The risky step is letting a model cause a side effect, an INSERT, based on its own reasoning. I wanted to build that honestly: the model decides and sequences, but every real action runs through my code, where it can be validated and refused.

Architecture

What it does

  • Tool-calling agent with a JSON-schema tool menu; the model sequences policy check → save autonomously
  • Real side effects — the agent calls SaveExpense and the C# layer performs an actual INSERT
  • RAG policy compliance via Gemini embeddings + pgvector cosine search
  • A 0.36 distance threshold rejects weak matches so unrelated expenses don't match the wrong policy
  • Structured output forced to strict JSON and parsed into typed C# records
  • Fallback parser that salvages the malformed XML-style tool calls some models emit
  • Stale-embedding handling — editing a policy clears its vector and forces a re-embed

How it works

The model proposes, the code acts

This is the mental model the whole project is built on. When the model “calls SaveExpense”, it has only written a message saying so — nothing has happened yet. My C# code reads that intent and performs the actual INSERT. That separation is what makes an acting agent safe to build: every side effect passes through code I control, where it can be validated, logged or refused.

finish_reason as the steering wheel

The agent loop runs up to five iterations, and finish_reason decides what happens next: "tool_calls" means act again, "stop" means we're done. State that has to survive across turns — the policy verdict, the saved row id — is declared outside the loop rather than inside it. Small detail, but it's the difference between an agent that can sequence work and one that forgets what it just did.

The threshold that prevents nonsense

Vector search always returns a nearest neighbour, even when nothing relevant exists — ask about a category with no policy and you'll still get the closest one back. A cosine distance guard of 0.36 rejects weak matches, so an unrelated expense fails to match rather than being judged against the wrong policy. Without this the agent is confidently wrong; with it, it says it doesn't know.

Defending against messy model output

Some models emit malformed XML-style tool calls instead of clean JSON. Rather than let the loop crash, a fallback parser salvages them. It is unglamorous work, and it is what separates a demo from something that survives real traffic.

What I took away

  • An agent that writes to a database needs the same review rigour as any privileged code path.
  • Similarity thresholds matter as much as the embedding model — nearest is not the same as relevant.
  • Forcing structured output turns model text into something a typed language can trust.
  • Assume models will emit malformed tool calls and handle it, rather than hoping they won't.
