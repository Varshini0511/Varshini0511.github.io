GitHub Agent

A multi-agent assistant built on an MCP server

An MCP server exposes GitHub as 22 tools; LangGraph agents use them to explain codebases with path:line citations, triage issues, review pull requests, diagnose failing CI, and open pull requests — behind an approval gate, guardrails and usage metering, reachable from a web UI or an HTTP/SSE API.

Live demo Source

Streamlit Community Cloud sleeps after inactivity — click “wake” if you see a sleep screen. It runs on Groq's free tier, so Supervisor mode can occasionally pause on a rate limit.

Solo — MCP server, agent wiring, RAG, approval flow, evals, UI

The problem

Letting a model act on a real GitHub account is useful and risky in equal measure. I wanted to build the whole thing the careful way: tools exposed through a proper protocol instead of ad-hoc glue, every write behind human approval, answers that cite the code they came from, and an evaluation set that checks the agent says “not found” instead of inventing a file. Then I kept going — hybrid retrieval, read-only DevOps specialists, and a signed webhook that triages a broken build on its own.

Architecture

What it does

  • MCP server exposing 22 GitHub tools over stdio, discovered by the agents rather than hard-coded
  • Supervisor routes to five specialists — repo_qa, issue_triage, code_writer, plus read-only ci_triage and pr_reviewer
  • Hybrid RAG over any repository: FAISS dense + BM25 fused with Reciprocal Rank Fusion, identifier-aware, cited by path:line
  • Human-in-the-loop: writes freeze the graph at an interrupt; approve or reject to resume, in the UI or over the API
  • Guardrails: secret and PII redaction both ways, and prompt-injection quarantine of tool output
  • DevOps pair returns structured reports; every evidence quote is tagged [verified] or [UNVERIFIED] against the real tool output
  • A signed CI webhook lets a failed build trigger triage on its own; HTTP/SSE API alongside the web UI
  • 100+ offline tests, including the real agent graph driven by a scripted fake model

How it works

Tools through a protocol, not glue

GitHub operations live in an MCP server rather than inside the agent. The agents launch it as a subprocess over stdio and discover its tools at startup, so adding a tool means editing one file, and any MCP-capable client could use the same server. The code is layered to match: github_client.py knows nothing about MCP or agents, server.py turns it into tools, and agent_core.py wires tools to a model — each layer testable on its own.

Two locks on every write

The seven state-changing tools are gated twice. A human-in-the-loop interrupt pauses the graph before any of them runs, and the Streamlit UI shows Approve and Reject buttons. Separately, an ALLOW_WRITES switch is checked inside the tool itself, so even an approved call does nothing unless writes are enabled. The HTTP API is held to the same bar — a request can't mutate a repo without ALLOW_WRITES and a separate /resume approval — and there is intentionally no tool to merge, delete, force-push or change repo settings. The code-writing specialist is also told never to touch the default branch: create a branch, write on it, open a pull request. Approval you can only trust in one place isn't approval.

Why a supervisor instead of one big agent

A single agent holding every tool makes each model call larger and gives smaller models more ways to choose wrongly — and one system prompt can't be good at reviewing code, triaging issues and reading CI logs all at once. So five specialists each get a focused prompt and only the tools they need — repo_qa, issue_triage, code_writer, and the read-only ci_triage and pr_reviewer — and the supervisor calls each as a single tool with a task string. Specialists share no memory with the supervisor or each other, so the task string has to carry everything — repo, issue numbers, file paths — which is context engineering in its plainest form.

Errors written for a model to read

The GitHub client retries what is worth retrying — rate limits and 5xx — with exponential backoff and jitter, and turns what isn't worth retrying (404, 401, 403) into messages that say what went wrong and what to try next. A second failure mode is subtler: the model occasionally emits a tool call that violates the schema, and a blind retry usually repeats the same mistake. A middleware hook instead parses the rejection, names exactly which arguments were missing or invalid, and feeds that back before retrying, up to three times.

Hybrid retrieval over a codebase

A repository is far bigger than a context window, so index_repo downloads the tarball, skips dependency and lock files, splits text into overlapping chunks and embeds them into a FAISS index. But dense search alone is weak on code: an exact identifier like a function name is a keyword problem, not a semantic one. So search_code also runs BM25 and fuses the two rankings with Reciprocal Rank Fusion, with identifier-aware weighting — the same fusion idea as the shopping search, applied to source. Every hit comes back with its path and starting line, so answers cite exactly where they came from.

DevOps specialists that quote their evidence

ci_triage reads a failed workflow run and returns a structured report — category, root cause, verbatim log evidence, a suggested fix and a confidence — while pr_reviewer returns a structured review with findings pinned to file, line and quote. Both are deliberately read-only: they diagnose, they don't fix, and fixing still routes through code_writer with approval. The part I'm proudest of is the honesty check: every quote is verified against what the tool actually returned and tagged [verified] or [UNVERIFIED], so a plausible-sounding but invented log line is marked as such instead of trusted. Logs are shrunk to the failing step and diffs are budgeted with real line numbers, so it fits free-tier limits.

A broken build that triages itself

A signed webhook endpoint lets a failed GitHub Actions run trigger ci_triage on its own, so a diagnosis is waiting before anyone asks. Safe by default: every delivery is verified with an HMAC signature, so a forged request is rejected, and because triage is read-only it can run unattended without any risk of a write. It's the difference between a tool you have to drive and one that does the first, boring step for you.

Evaluating the failure mode, not just the happy path

A golden set scores real questions two ways, and a case passes only if both agree: deterministic checks (did it call the expected tool, does the answer contain or avoid specific strings) and a separate LLM judge scoring against a plain-English rubric. One case asks for the source of a file that doesn't exist and fails the agent if any code appears in the answer. The runner exits non-zero on any failure, so it doubles as a CI gate.

Bridging an async agent into Streamlit

Streamlit reruns the whole script on every click, but the agent's MCP subprocess and async SQLite connection both need the same asyncio task to stay alive for the whole session. A naive bridge that opens the agent in one call and reuses it in later calls breaks silently — the connection's worker thread is torn down once nothing references it. The fix is to hold the entire session inside one long-lived task on a dedicated background thread, fed by a queue, so any rerun can submit work and wait for the result.

What I took away

  • A protocol layer like MCP separates what an agent can do from how the agent is built.
  • Dense search alone is weak on code — an exact identifier is a keyword problem, so hybrid retrieval wins.
  • Approvals are only trustworthy when they're enforced in more than one place.
  • Make an agent quote its evidence and verify the quote — a confident, invented log line is the real danger.
  • An evaluation set should test the failure you're most afraid of — here, inventing code.
