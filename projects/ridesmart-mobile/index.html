RideSmart Mobile

Cross-platform ride comparison in Expo and React Native

The cross-platform sibling: an Expo and React Native app, in TypeScript, that compares estimated fares across the four ride apps and then hands off to the chosen one with the route pre-filled. One codebase configured for Android, iOS and web.

Source

No hosted demo — run it from source with Expo (npx expo start) on a device, simulator or in the browser.

Solo — Expo app, fare model, deep-link hand-off, on-device history

The problem

The Android build needs a sensitive permission and only runs on Android. I wanted the same comparison somewhere it could run anywhere, with a stricter promise: estimate carefully, label it as an estimate, and leave the actual booking to the ride app rather than automating it.

Architecture

What it does

  • Expo Router app with three tabs: compare, history and settings
  • Estimates fares from per-provider fare cards — base, per-km, per-minute, minimum — with time-of-day and weekend surge, shown as a ±10% range
  • Place search through OpenStreetMap Nominatim, plus current-location pickup with reverse geocoding
  • Filters by ride type, highlights the best quote and shows the most you could save
  • Hands off to Uber, Ola, Rapido or Namma Yatri via deep links with pickup and drop pre-filled, falling back to the Play Store or the web
  • On-device SQLite history with per-provider price statistics, with a separate web implementation of the storage layer
  • TypeScript throughout, with shared types for providers, ride types and quotes

How it works

Estimating without overclaiming

Without the accessibility approach there is no way to see a live price, so this app doesn't pretend to. Fares come from per-provider fare cards, with surge and ETA sampled within time-of-day ranges, and every number is shown as a range with a note in settings saying they are estimates. The comparison is useful for ranking providers against each other; it is deliberately not presented as a quote.

Deep links as the integration

Rather than automate another app, the hand-off is a URL: each provider has its own scheme with the pickup and drop coordinates and addresses filled in. The code checks whether the app can open the link, falls back to the Play Store when it isn't installed and to the provider's website after that, and returns whether the app opened so the UI can offer to install it.

One codebase, platform-specific storage

History lives in expo-sqlite on a device, which doesn't exist on the web, so the storage module has a native implementation and a separate web one that the bundler picks per platform. The schema holds comparisons, their quotes and bookings; route history matches within a small coordinate window, and price statistics aggregate average, minimum, maximum and count per provider and ride type.

Why there are two apps

This and the Android build make opposite trade-offs on purpose. Android sees real prices and can race bookings, at the cost of a permission and a dependence on each app's on-screen labels. This one never sees a live price, but it runs on any platform, asks for nothing sensitive and cannot break when a ride app redesigns its screens.

What I took away

  • An estimate labelled as an estimate is a feature; a guess dressed as a price is a bug.
  • A deep link is a thin, durable integration compared with automating another app's UI.
  • Platform-specific modules keep one codebase clear about what only exists on a device.
  • Choosing less capability on purpose is a design decision — this build trades live prices for reach and safety.
