Multi-Agent Travel Planner

LangGraph orchestration with a reflection loop

A LangGraph workflow that plans trips end to end: a guardrail, a planner that decomposes the request, specialised subagents that run in parallel and pick their own tools, a synthesiser, and a critic that reviews against budget and loops back for revisions.

The problem

Trip planning spans several domains — flights, hotels, activities and visas each need different sources and different reasoning. One prompt doing all four does all four badly. It's a natural fit for real orchestration: decompose the task, fan out to specialists, then have something check the result before the user sees it.

Architecture

What it does

  • Parallel fan-out / fan-in across flights, hotels, activities and visa subagents
  • Reflection loop — the critic sends plans back to the planner when they miss budget
  • Human-in-the-loop: the graph pauses on interrupt so you can approve or edit the plan
  • Long-term semantic memory across trips via pgvector + Gemini embeddings
  • Dynamic tool selection — each subagent chooses web search vs currency conversion
  • Provider fallback: Groq primary, Gemini fallback, with graceful degradation
  • Evaluation harness with deterministic checks plus an LLM-as-judge rubric

How it works

Why a graph instead of a chain

A linear chain can't express what this workflow needs: four branches running at once, then joining, then a conditional edge that can send everything backwards. LangGraph makes state, nodes and edges explicit, so parallel fan-out, fan-in and the critic's loop back to the planner are all just topology rather than control-flow gymnastics.

The reflection loop

The critic reviews the synthesised plan against budget and constraints. If it fails, the graph routes back to the planner with the critique attached rather than returning something the user has to reject themselves. This is the single change that most improved output quality — a first draft checked by a second pass beats one very carefully prompted attempt.

Context engineering

Each agent sees only what it needs. The hotel subagent doesn't receive flight research, and the critic doesn't receive raw search dumps. Keeping context narrow cuts token cost, but more importantly it cuts distraction — agents given less irrelevant material make fewer irrelevant decisions.

Memory across trips

Past trips are embedded with Gemini and stored in pgvector, so the planner can recall relevant preferences from earlier plans — a standing dislike of early flights, a preferred hotel tier — without those being repeated in the prompt. Trip state itself persists through a LangGraph Postgres checkpointer, so a plan survives a refresh.

What I took away

  • Explicit graph state is what makes multi-agent systems debuggable rather than mysterious.
  • A critic that can send work backwards beats a longer prompt almost every time.
  • Parallel subagents need narrow context, or they drift toward each other's jobs.
  • Provider fallback isn't optional once you depend on a free tier.
